# Выкладка на боевой сервер

Как устроен прод и что делать при каждом обновлении.

## Что где находится

| | |
|---|---|
| Сервер | Ubuntu VPS, `159.194.230.39` |
| Папка проекта | `/var/www/s-poryadok` |
| Приложение | Gunicorn через сокет `/run/gunicorn.sock`, служба `gunicorn` |
| Веб-сервер | Nginx: SSL, статика, прокси на сокет |
| Сертификат | Let's Encrypt (certbot), `/etc/letsencrypt/live/s-poryadok.ru/` |
| База | SQLite, `/var/www/s-poryadok/db.sqlite3` |
| Боевая ветка | `main` |

Локальная разработка идёт в отдельных ветках, но на сервер уезжает только `main`.

## 1. Локально: слить работу в `main`

```powershell
# зафиксировать в своей ветке
git add .
git commit -m "Описание изменений"
git push origin <имя-ветки>

# влить в main
git checkout main
git pull origin main
git merge <имя-ветки>
git push origin main
```

**Если истории разошлись** и merge отказывается работать:

```powershell
git pull origin main --allow-unrelated-histories
```

Дальше разрешить конфликты в PyCharm (`Git → Resolve Conflicts`) и закоммитить.

## 2. На сервере: обновить

```bash
ssh root@159.194.230.39

git pull origin main
source venv/bin/activate

pip install -r requirements.txt      # только если менялись зависимости
```

## 4. Конфигурация Nginx

Рабочая версия конфига хранится в репозитории:
**`deploy/nginx/s-poryadok.conf`**. Обновление на сервере:

```bash
cd /var/www/s-poryadok && git pull origin main
sudo cp /etc/nginx/sites-available/default /etc/nginx/sites-available/default.bak
sudo cp deploy/nginx/s-poryadok.conf /etc/nginx/sites-available/default
sudo nginx -t && sudo systemctl reload nginx
```

Откатиться, если что-то пошло не так:

```bash
sudo cp /etc/nginx/sites-available/default.bak /etc/nginx/sites-available/default
sudo nginx -t && sudo systemctl reload nginx
```

Ниже — сокращённый вид того же конфига для быстрого просмотра:

```nginx
# HTTPS: Django + SSL
server {
    listen 443 ssl;
    listen [::]:443 ssl ipv6only=on;

    server_name s-poryadok.ru www.s-poryadok.ru;

    ssl_certificate     /etc/letsencrypt/live/s-poryadok.ru/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/s-poryadok.ru/privkey.pem;
    include             /etc/letsencrypt/options-ssl-nginx.conf;
    ssl_dhparam         /etc/letsencrypt/ssl-dhparams.pem;

    location /static/ {
        alias /var/www/s-poryadok/staticfiles/;
    }

    location /media/ {
        alias /var/www/s-poryadok/media/;
    }

    location / {
        include proxy_params;
        proxy_pass http://unix:/run/gunicorn.sock;
    }
}

# HTTP -> HTTPS
server {
    listen 80;
    listen [::]:80;

    server_name s-poryadok.ru www.s-poryadok.ru;

    if ($host = www.s-poryadok.ru) { return 301 https://$host$request_uri; }
    if ($host = s-poryadok.ru)     { return 301 https://$host$request_uri; }

    return 404;
}
```

Проверить конфиг перед перезагрузкой: `sudo nginx -t`.

## 5. Настройки Django на проде

В `/var/www/s-poryadok/.env` должно быть как минимум:

```
DEBUG=False
SECRET_KEY=длинная-случайная-строка
```

**Про `SECURE_SSL_REDIRECT`.** Редирект с http на https уже делает Nginx, так что
включать его ещё и в Django не нужно — оставьте `False`. Django всё равно понимает,
что соединение защищённое: `proxy_params` передаёт заголовок `X-Forwarded-Proto`,
а `SECURE_PROXY_SSL_HEADER` в настройках его читает. От этого зависят абсолютные
адреса в OG-тегах и в `canonical`, поэтому `DEBUG=False` на проде обязателен.

**Про HSTS.** По умолчанию выключен (`SECURE_HSTS_SECONDS=0`). Включать —
осознанно и последним: браузеры посетителей запомнят настройку на год,
и откатить её будет практически невозможно.

## Сайт перестаёт отвечать: как искать причину

Если сайт ложится и помогает только перезагрузка VPS, диагноз ставится
не по догадкам, а по двум вещам: что показывают логи и работает ли ssh
в момент поломки.

### Первое, что надо выяснить

**Работает ли `ssh root@159.194.230.39`, пока сайт не отвечает?**
Этот один факт делит поиск пополам:

- **ssh работает** — значит сервер жив, проблема в nginx или gunicorn.
  Смотреть `systemctl status gunicorn`, `journalctl -u gunicorn -n 50`,
  `/var/log/nginx/error.log`.
- **ssh тоже не отвечает** — проблема ниже уровня приложения. Python-код
  не может оборвать вам ssh: значит перекрыт доступ к машине целиком.

### Если пропадает и ssh: блокировка вашего адреса

Когда с одного устройства разом отваливаются и сайт, и ssh, а через
некоторое время само чинится, — чаще всего это не поломка, а срабатывание
защиты: fail2ban или фильтр хостинга внёс ваш адрес в бан. «Подождать,
и заработает» — это истёкшее время бана.

Проверить:

```bash
sudo fail2ban-client status                    # какие правила включены
sudo fail2ban-client status sshd               # и кто забанен
sudo fail2ban-client status nginx-botsearch
sudo iptables -L -n | grep -i -E 'DROP|REJECT' | head -30
sudo ipset list 2>/dev/null | head -20
```

Разбанить свой адрес:

```bash
sudo fail2ban-client set sshd unbanip ВАШ_IP
sudo fail2ban-client set nginx-botsearch unbanip ВАШ_IP
```

Свой адрес можно узнать на телефоне, открыв `2ip.ru`.

Чтобы себя больше не банило, добавьте свои адреса в исключения —
`/etc/fail2ban/jail.local`:

```
[DEFAULT]
ignoreip = 127.0.0.1/8 ::1 ВАШ_ДОМАШНИЙ_IP
```

```bash
sudo systemctl restart fail2ban
```

Заодно посмотрите, за что банило:

```bash
sudo grep -i ban /var/log/fail2ban.log | tail -30
sudo awk '$9 ~ /^(404|403|444)$/ {print $7}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head
```

**Про 404 и iOS.** Safari на айфоне сам, помимо разметки, запрашивает
`/apple-touch-icon.png`, `/apple-touch-icon-precomposed.png` и `/favicon.ico`.
Если этих файлов нет, один заход с телефона даёт несколько 404 подряд —
а такая серия для fail2ban выглядит как перебор адресов ботом. Файлы
и маршруты для них добавлены в проект, но если правило уже настроено
агрессивно, стоит его смягчить.

### РАЗГАДКА: фильтрация ТСПУ и приветствие TLS 1.3

3 августа поддержка хостера подтвердила причину: новые правила
фильтрации ТСПУ ломают доступность части ресурсов. Рекомендация —
отключить на сайте поддержку TLS 1.3 и оставить только TLS 1.2.

Это точно совпадает с тем, что показали перехваты. Приветствие
браузера по TLS 1.3 крупное и не помещается в один сетевой пакет.
Оборудование фильтрации разбирает первый пакет, а продолжение
отбрасывает. Сервер получает половину приветствия, ждёт остаток и
молчит — что мы и наблюдали 26 раз подряд, всегда ровно на границе
одного пакета. Приветствие по TLS 1.2 втрое меньше, влезает целиком
и проходит.

#### Как отключить TLS 1.3 — и как НЕ надо

**Ловушка.** Кажется, что достаточно дописать `ssl_protocols TLSv1.2;`
после строки `include /etc/letsencrypt/options-ssl-nginx.conf;`. Это не
работает.

`ssl_protocols` в nginx — не значение, а **набор флагов**. Вторая такая
строка в том же блоке не заменяет первую, а добавляется к ней. Файл
Let's Encrypt задаёт `TLSv1.2 TLSv1.3`, наша строка добавляет `TLSv1.2`
поверх — и TLS 1.3 остаётся включённым. Единственный признак —
безобидное на вид предупреждение при проверке:

```
[warn] duplicate value "TLSv1.2" in /etc/nginx/sites-enabled/default:36
```

Проверка после такой правки честно показывает, что ничего не изменилось:

```
New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384
```

**Как правильно.** Убрать версию можно только там, где она назначается.
Поэтому `include` заменён на явные настройки — см.
`deploy/nginx/s-poryadok.conf`. Второй вариант, попроще, но менее
надёжный: отредактировать сам `/etc/letsencrypt/options-ssl-nginx.conf`,
имея в виду, что обновление certbot может вернуть файл к исходному виду.

#### Куда именно вписывать

`/etc/nginx/sites-available/default`:

```nginx
server {
    listen 443 ssl;
    listen [::]:443 ssl ipv6only=on;
    server_name s-poryadok.ru www.s-poryadok.ru;

    ssl_certificate     /etc/letsencrypt/live/s-poryadok.ru/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/s-poryadok.ru/privkey.pem;
    include             /etc/letsencrypt/options-ssl-nginx.conf;
    ssl_dhparam         /etc/letsencrypt/ssl-dhparams.pem;

    # Временно, пока действуют правила фильтрации ТСПУ.
    # Приветствие TLS 1.3 не помещается в один пакет, и его продолжение
    # отбрасывается по дороге. Строка должна стоять ПОСЛЕ include выше.
    ssl_protocols TLSv1.2;
    ...
```

```bash
sudo nginx -t && sudo systemctl reload nginx
```

#### Нужен restart, а не reload

Смена набора протоколов через `systemctl reload nginx` не применяется:
проверка продолжает показывать `TLSv1.3` при полностью правильном
конфиге. Помогает только полный перезапуск:

```bash
sudo systemctl restart nginx
```

Перерыв в работе — доли секунды.

#### Заодно: лишние конфиги и старые протоколы

`nginx -T` печатает итоговый конфиг со всеми включёнными файлами —
это единственный надёжный способ увидеть, что на самом деле работает:

```bash
sudo nginx -T 2>/dev/null | grep -nE 'ssl_protocols|listen .*443'
```

На сервере нашлось два наследства.

**Мёртвый конфиг старого проекта** `/etc/nginx/sites-enabled/poryadok`:
слушал порт 80, проксировал в несуществующий
`/var/www/poryadok_project/poryadok.sock`, да ещё с ошибочным
`server_name http://s-poryadok.ru/`. Отключён:

```bash
sudo rm /etc/nginx/sites-enabled/poryadok
```

Убрана только ссылка, сам файл лежит в `sites-available`.

**Устаревшие протоколы в `/etc/nginx/nginx.conf`**, строка 34:

```nginx
ssl_protocols TLSv1 TLSv1.1 TLSv1.2 TLSv1.3;
```

TLSv1 и TLSv1.1 давно небезопасны. На наш сайт это не влияет — блок
`server` задаёт свой набор и перекрывает общий, — но если появится
второй сайт без своих настроек, он унаследует именно эту строку.
Привести к:

```nginx
ssl_protocols TLSv1.2;
```

#### Проверка, что применилось

```bash
echo | openssl s_client -connect 127.0.0.1:443 -servername s-poryadok.ru 2>/dev/null \
  | grep -E 'Protocol|Cipher'
```

Должно быть `TLSv1.2`. И попытка навязать 1.3 должна отвергаться:

```bash
echo | openssl s_client -connect 127.0.0.1:443 -servername s-poryadok.ru \
  -tls1_3 2>&1 | grep -E 'Protocol|alert|failure' | head -3
```

Затем — с телефона открыть сайт несколько раз в течение 10–15 минут.

#### Что это стоит

Ничего не ломается: TLS 1.2 поддерживают все браузеры, ни один
посетитель доступ не теряет. Защита остаётся стойкой — TLS 1.2 с
современными шифрами был основой интернета до недавнего времени.

Это временная мера. Когда правила фильтрации изменятся, строку надо
убрать и вернуть TLS 1.3 — он быстрее устанавливает соединение.
Пометка об этом стоит в конфиге рядом со строкой.

#### Оговорка

Одна проверка этой версии противоречит: `curl --tls-max 1.2` с
компьютера в момент отказа тоже не проходил, хотя приветствие там
маленькое. Возможно, в тот момент отказ был полным по другой причине,
возможно, фильтрация тогда работала жёстче. Поэтому после изменения
нужно понаблюдать не пять минут, а хотя бы час: отказ прерывистый, и
короткое затишье ничего не доказывает.

### Заявки не приходят в Telegram

Заявка всегда сначала ложится в базу и только потом уходит в Telegram —
так что «не пришло уведомление» никогда не значит «заявка потеряна».
Всё лежит в админке, в разделе «заявки», со столбцом «в Telegram».

Найти обрыв по шагам:

```bash
cd /var/www/s-poryadok
source venv/bin/activate
python manage.py check_telegram          # проверка
python manage.py check_telegram --send   # и сразу проверочное сообщение
```

Команда проходит цепочку целиком: настройки → сеть до api.telegram.org →
бот отвечает → доступ в чат → отправка. И говорит, на каком шаге обрыв.

Частые причины, по убыванию:

0. **`.env` вообще не читался.** В `core/settings.py` функция `load_dotenv`
   была импортирована, но не вызвана. Настройки при этом брались из
   значений по умолчанию, всё работало — и молчание Telegram было
   единственным внешним признаком. Исправлено: `load_dotenv(BASE_DIR / '.env')`
   с явным путём, потому что без пути dotenv ищет файл от текущей папки,
   а команды на сервере запускаются откуда придётся.
1. **`.env` на сервере не заполнен.** Файл в репозиторий не попадает,
   поэтому переменные надо вписать прямо на сервере, а потом обязательно
   `sudo systemctl restart gunicorn` — без перезапуска Django их не увидит.
   Локальный `.env` в PyCharm на сервер не уезжает: это два разных файла.
2. **Диалог с ботом не начат.** Бот не может написать первым. Откройте
   его в Telegram и нажмите «Запустить».
3. **Неверный `TELEGRAM_CHAT_ID`.** Свой id даёт `@userinfobot`. Для
   группы id начинается с минуса, вида `-1001234567890`, и бота надо
   сначала добавить в группу.
4. **Сервер не достучался до Telegram.** Тогда шаг «сеть» не пройдёт.

Заявки, которые не ушли, видно так:

```bash
python manage.py shell -c "from landing.models import Lead; print(Lead.objects.filter(delivered_to_telegram=False).count())"
```

### Стили не обновились после выкладки

Nginx отдаёт статику с кэшем на 30 дней. Пока имя файла не менялось,
браузер посетителя честно показывал старый `site.css` — сайт «разъезжался»
именно поэтому, а не из-за вёрстки.

Решено отпечатками: `collectstatic` собирает файл под именем вида
`site.19ced5cb.css`, и новая сборка получает новое имя. Кэш перестаёт быть
проблемой, а `{% static %}` подставляет нужное имя сам.

Включается только при `DEBUG=False` — в разработке отпечатки лишь заставляли
бы гонять `collectstatic` после каждой правки.

**Что это меняет в выкладке:** `collectstatic` теперь обязателен всегда,
даже если менялся только CSS.

**Если забыть — сайт больше не ляжет.** Так было ровно один раз: обычное
хранилище с отпечатками поднимает исключение, не найдя файл в справочнике,
а справочник читается и при отрисовке страниц, и при загрузке маршрутов.
Одна иконка обрушивала весь сайт с ошибкой:

```
ValueError: Missing staticfiles manifest entry for 'landing/img/favicon.ico'
```

Причём `collectstatic` в этом состоянии тоже не запускался — он прогоняет
проверки и импортирует те же маршруты. Выход был только через
`python manage.py collectstatic --noinput --skip-checks`.

Теперь этого не повторится: `core/storage.py` при неудаче отдаёт путь
без отпечатка и пишет в журнал предупреждение. Файл откроется, просто
может прийти из кэша. Размен сознательный — отпечаток на одном файле
не стоит лежащего сайта. На это есть тест: страницы должны открываться
при полностью отсутствующей собранной статике.

Если стили всё же не поменялись, проверьте по порядку:

```bash
python manage.py collectstatic --noinput
ls staticfiles/landing/css/          # должны быть site.css и site.ХЭШ.css
grep -o 'site\.[a-z0-9]*\.css' staticfiles/staticfiles.json | head -1
sudo systemctl restart gunicorn
```

И откройте страницу с обходом кэша: `Ctrl+F5`.

### Оплата клуба через GetPlatinum

В `.env` на сервере:

```
GETPLATINUM_API_KEY=ключ из личного кабинета
GETPLATINUM_BASE_URL=https://ВАШ_АККАУНТ.getplatinum.ru/api/public/pay
```

Ключ: личный кабинет → Настройки → шестерёнка у организации. Адрес свой
у каждого аккаунта, `ВАШ_АККАУНТ` — имя, под которым вы зарегистрированы.

После правки `sudo systemctl restart gunicorn`. Дальше страница клуба
сама перестаёт быть формой заявки и ведёт на оплату.

Проверить подключение, ничего не оплачивая:

```bash
python manage.py check_getplatinum          # настройки и ключ
python manage.py check_getplatinum --link   # и пробная ссылка на 10 ₽
```

Команда проходит цепочку по шагам: настройки → ключ принят → организация
видна → ссылка на оплату создаётся. Пробный заказ остаётся неоплаченным
и ни на что не влияет.

**API не заработает, пока не одобрена заявка на подключение организации** —
это отдельный шаг в личном кабинете GetPlatinum, помимо регистрации.
Если команда спотыкается на втором шаге, начинать надо с этого.

Адрес для уведомлений передаётся в каждом платеже, настраивать его в
личном кабинете не нужно:

```
https://s-poryadok.ru/pay/getplatinum/webhook/
```

**Как проходит оплата.** Человек выбирает тариф → мы создаём заказ через
`/init-payment-url` и уводим его на платёжную форму GetPlatinum → после
оплаты приходит уведомление → мы переспрашиваем `/status` → подписка
включается и выдаётся одноразовая ссылка в канал.

**Про подпись уведомлений — важно.** Пример подсчёта в документации
GetPlatinum противоречив: заявлена длина строки 122 символа, показана
строка в 140, а приведённая контрольная сумма не получается ни из
показанной строки, ни из честно отсортированной по описанному алгоритму.
Воспроизвести их подсчёт «вслепую» невозможно.

Поэтому подпись пока **совещательная**: несовпадение пишется в журнал,
а решает переспрос `/status` — подделать его нельзя, ответ приходит с
сервера GetPlatinum по нашему ключу API. Размен здесь несимметричный:
лишний вызов `/status` не стоит ничего, а отвергнутое настоящее
уведомление означает списанные деньги без доступа.

После первой настоящей оплаты посмотрите журнал:

```bash
grep -i "подпись не совпала" /var/www/s-poryadok/logs/app.log
```

Пусто — подпись сходится, можно включать строгую проверку:

```
GETPLATINUM_STRICT_CHECKSUM=True
```

Есть записи — пришлите мне строку из журнала, там наша подпись и начало
пришедшей; по ним видно, чем именно их подсчёт отличается от описанного.

**Возвраты** делаются в личном кабинете GetPlatinum. Автоматически
подписку они не закрывают: снимите её вручную в админке, статус
«Отменена».

### Клуб: канал, id и вход через Telegram

**Найти id канала.** Telegram не даёт списка чатов, но любое событие
приносит id. Бот должен быть админом канала, и в канале должен быть
хотя бы один пост:

```bash
python manage.py telegram_chats
```

Выведет все чаты с их id. Личка — без минуса, канал — с минусом. В `.env`:

```
TELEGRAM_CHAT_ID=123456789            # личка: сюда падают заявки
TELEGRAM_CLUB_CHAT_ID=-1001234567890  # канал: отсюда выдаются приглашения
TELEGRAM_BOT_USERNAME=имя_бота_без_собаки
```

Затем `sudo systemctl restart gunicorn`.

**Зачем вход через Telegram.** Ради числового id человека. Ник — просто
подпись, её меняют за секунду, и по нику API не умеет ни приглашать, ни
исключать. Пока id неизвестен, `expire_club` может только написать
«уберите вручную». После входа через Telegram доступ закрывается сам.

Кнопка входа стоит на странице клуба. Чтобы виджет работал, домен нужно
привязать к боту: у `@BotFather` команда `/setdomain`, затем выбрать бота
и прислать `s-poryadok.ru`.

**Как это устроено.** Telegram возвращает данные обычной строкой запроса —
подделать её может кто угодно. Подлинность доказывает поле `hash`:
Telegram подписывает им остальные поля ключом, который знает только
владелец бота. Мы считаем ту же подпись у себя и сравниваем; данные
старше суток отбрасываем. Всё, что не подтвердилось, считается подделкой —
на это есть отдельные тесты, включая попытку подменить чужой id.

### Сайт не открывается: с чего начинать всегда

Не гадать, а измерить. Сайт — это четыре вложенных слоя, и сломан всегда
какой-то один. Скрипт стучится в каждый по очереди, снаружи внутрь;
первый неответивший слой и есть виновник.

```bash
cd /var/www/s-poryadok
sudo bash scripts/down.sh
```

Запускать **в момент, когда сайт не открывается** — по работающему
серверу отчёт бесполезен. Результат сохраняется в `logs/down.txt`.

Как читать:

| Что не ответило | Кто виноват |
|---|---|
| слой 1, сокет gunicorn | Django или gunicorn — смотреть `logs/app.log` |
| слой 2, nginx по HTTP | nginx — смотреть `/var/log/nginx/error.log` |
| слой 3, nginx по HTTPS | TLS: истёк сертификат или сломан конфиг |
| слой 4, но 1–3 живы | **сервер исправен, режется снаружи** — сеть хостера |
| все четыре живы | проблема у конкретного посетителя, не на сервере |

Строка «слои 1–3 живы, режется снаружи» — самая важная. Она означает,
что чинить на сервере нечего и надо писать хостеру, приложив отчёт.

#### Доходят ли пакеты вообще

Все замеры выше делаются **изнутри** сервера и потому имеют слепое пятно:
если пакеты посетителя до сервера не долетают, изнутри это неотличимо от
тишины — сервер здоров и просто никого не видит.

```bash
sudo bash scripts/sniff.sh 120
```

Пока идёт отсчёт, надо с телефона обновлять сайт. Скрипт слушает порты
80 и 443 и записывает всё, что пришло.

| Что поймано | Что это значит |
|---|---|
| ничего | пакеты не доходят — режут выше сервера, у хостера |
| `[S]` без `[S.]` | сервер не отвечает на запрос соединения |
| `[S]` и `[S.]`, дальше тишина | ответ не доходит обратно — размер пакета |
| данные, потом `[R]` на середине | ответ рвётся при передаче — размер пакета |
| всё прошло, а сайт не открылся | дело не в сети |

Пустой улов — самый важный результат: он означает, что чинить на сервере
нечего, и надо писать хостеру. Обязательно упомянуть, что ssh на порт 22
в это же время работает: значит адрес живой, а режутся именно веб-порты.

#### Посторонний, который стучится без остановки

В той же записи:

```
45.202.3.134          1209 соединений, все без единого байта данных
```

Тысяча двести соединений за два часа, около одиннадцати в минуту, и ни

Само по себе это может быть безобидной проверкой доступности, а может
быть тем, из-за чего защита хостера считает адрес сервера целью атаки
и начинает подчищать трафик — что и выглядит как случайная потеря
пакетов у обычных посетителей.

Сначала выяснить, кто это:

```bash
whois 45.202.3.134 | grep -i -E 'orgname|netname|country|descr'
for f in logs/cap-*/web.pcap*; do
  tcpdump -r "$f" -nn -tttt 'host 45.202.3.134' 2>/dev/null
done | head -20
```

Если это не служба хостера — закрыть:

```bash
sudo iptables -I INPUT -s 45.202.3.134 -j DROP
sudo netfilter-persistent save
```

Снять обратно: `sudo iptables -D INPUT -s 45.202.3.134 -j DROP`.

#### Проверка, что теряет не сам сервер

Перехват видит только то, что доехало до сетевой карты. Если пакет
отбрасывает карта, драйвер или очередь ядра, в перехвате его не будет —
и со стороны это неотличимо от потери в сети.

```bash
sudo bash scripts/drops.sh
```

Все нули в `ListenOverflows`, `BacklogDrop`, `RcvPruned` и в `dropped`
у сетевой карты — значит сервер ничего не теряет, и потеря происходит
до него. Ненулевые значения — чинится на месте.

Замер 3 августа: сетевая карта чиста (`dropped 0`, `errors 0`), все
очереди ядра по нулям — сервер справляется с нагрузкой полностью. Но
один счётчик оказался ненулевым:

```
TcpInCsumErrors              76
```

**76 пакетов пришли повреждёнными и были молча выброшены ядром.** У
исправного канала здесь ноль. Для отправителя повреждённый пакет
неотличим от потерянного: он не получает подтверждения и ждёт. Симптом
получается ровно тот, что мы ловим, — «пакет как будто не дошёл».

**Как эту цифру НЕ надо проверять.** Поиск слова `incorrect` в выводе
`tcpdump -vv` без указания направления бесполезен: у всех **исходящих**
пакетов контрольная сумма в перехвате всегда «неверна». Её вычисляет
сама сетевая карта, уже после того, как пакет попал в перехват. Это
нормальное поведение любого сервера, а не поломка.

Смотреть можно только на **входящие**, и только при полной записи
пакета — по обрезанному (`-s 128`) сумму посчитать невозможно:

```bash
for f in logs/cap-*/web.pcap*; do
  tcpdump -r "$f" -nn -vv 'src host АДРЕС_ПОСЕТИТЕЛЯ and tcp' 2>/dev/null
done | grep -ic 'incorrect'
```

**Как проверять правильно.** Проще и надёжнее следить за самим
счётчиком ядра — он считает настоящие входящие пакеты:

```bash
cd /var/www/s-poryadok
sudo bash scripts/csum.sh &
tail -f logs/csum.log
```

Скрипт отмечает время каждого прироста. Если счётчик растёт ровно в те
минуты, когда сайт отваливается, — причина найдена. Если он стоит на
месте, а сайт при этом лежит, то повреждения к делу не относятся.

**Замер 3 августа, результат отрицательный.** Счётчик растёт примерно
на один-два пакета в минуту, и **одинаково** — и когда сайт работает,
и когда висит:

```
16:31 → 16:41   +12 пакетов за 10 минут   сайт работал      1,2 в минуту
16:53 → 17:00   +7  пакетов за 6 минут    сайт висел        1,2 в минуту
```

Один-два повреждённых пакета в минуту не могут объяснить отказ: во
время зависания браузер делает по два десятка попыток рукопожатия за
пару минут, и все они срываются. Совпадения по времени нет, объёма не
хватает на порядок. **Повреждение пакетов — не причина.**

Но и не пустяк. Полторы тысячи повреждённых пакетов в сутки для
канала в дата-центре — много, и портит данные обычно то же самое, что
их теряет: плохое соединение, стык или оборудование по пути. Поэтому
цифра остаётся в письме хостеру как признак состояния канала, но уже
не как объяснение.

#### Непрерывная запись вместо ловли с секундомером

Отказ прерывистый и случается тогда, когда его никто не ловит. Ждать
его вручную бессмысленно — поэтому пишем всегда, по кольцу:

```bash
cd /var/www/s-poryadok
sudo bash scripts/record.sh start     # запустить один раз и забыть
sudo bash scripts/record.sh status    # проверить, идёт ли
```

Занимает не больше 120 МБ и затирает старое. Пишутся только заголовки
пакетов, не содержимое страниц.

Когда сайт в следующий раз отвалится — зайти по ssh и отложить запись,
пока её не затёрло:

```bash
sudo bash scripts/record.sh save
```

Теперь доказательство собирается само, а от владельца нужна только
отметка времени.

#### Отказ прерывистый

Замеры 3 августа показали характер поломки: после перезапуска nginx сайт
открывается около минуты, потом перестаёт — и на телефоне, и на
компьютере. Мелкий файл `robots.txt` открылся один раз и тоже перестал.

Отсюда два вывода, важных для любой дальнейшей проверки:

1. **Одиночная проверка ничего не доказывает.** Именно из-за
   прерывистости каждая версия сначала подтверждалась, а потом
   рассыпалась: совпадение принималось за причину.
2. **Все проверки надо делать подряд, за один заход**, и обязательно
   в момент отказа.

#### Если все четыре слоя ответили 200

Значит сервер исправен целиком, и вопрос переходит к другому: а что
получил сам посетитель? Журнал gunicorn на этот вопрос не отвечает — он
показывает только, что Django досчитал страницу и отдал её nginx. Дошла
ли она до браузера, знает лишь nginx.

```bash
sudo bash scripts/client.sh                 # все посетители
sudo bash scripts/client.sh 2.26.13.3       # только свой адрес
```

Что искать:

* **код 499** — браузер закрыл соединение, не дождавшись ответа.
  Много таких — ответ не доходит.
* **размер отданного** — на главной обычно около 39 000 байт (или около
  8 000 при включённом сжатии). Обрывочные значения, не совпадающие
  с обычным размером, означают, что ответ рвётся на полпути.

#### Проверка размером

Если запрос до сервера доходит (виден в журнале с кодом 200), а страница
в браузере не появляется — ломается обратный путь. Разделить «не доходит
вообще» и «не доходит крупное» можно за пять секунд, открыв с телефона
два адреса подряд:

| Адрес | Размер | Что значит |
|---|---|---|
| `https://s-poryadok.ru/robots.txt` | ~108 байт, один пакет | открылось — сеть до сервера в порядке |
| `https://s-poryadok.ru/` | ~39 000 байт, десятки пакетов | не открылось — виноват размер ответа |

Мелкое открывается, крупное нет — это доказанная зависимость от размера
пакета, и лечится она на сервере (`tcp_mtu_probing`, clamp MSS, сжатие).
Не открывается ни то ни другое — размер ни при чём, дело в маршруте.

#### Сжатие ответа

Главная страница отдаётся примерно 39 КБ текста. Сжатие уменьшает её
примерно вчетверо — это и быстрее для посетителя, и вчетверо меньше
пакетов в обратную сторону. В `/etc/nginx/nginx.conf`:

```nginx
gzip on;
gzip_vary on;
gzip_min_length 512;
gzip_comp_level 5;
gzip_types text/plain text/css application/json application/javascript
           text/xml application/xml image/svg+xml;
```

```bash
sudo nginx -t && sudo systemctl reload nginx
```

Шрифты `woff2` сжимать не нужно — они уже сжаты.

#### Что было проверено и отпало

История поисков, чтобы не ходить по кругу второй раз:

* **Нехватка памяти** — нет. Свободно 1,5 ГБ, ядро никого не убивало.
* **fail2ban банил посетителей** — нет. Единственная тюрьма `sshd`,
  журналы nginx она не читает, а `banaction` привязан к порту ssh.
* **Пачка параллельных запросов от страницы** — нет. Со страницы убрали
  CSS и скрипты, остался один запрос — поведение не изменилось.
* **IPv6** — нет. У домена только `A`-запись, AAAA нет вовсе,
  по IPv6 к сайту никто и не ходит.
* **VPN на телефоне и размер пакета (PMTU)** — нет. VPN стоит и на
  компьютере тоже, и там сайт открывается; без VPN на телефоне сайт
  всё равно не открылся.
* **Устройство вообще ни при чём** — сайт перестаёт открываться
  и на телефоне, и на компьютере одновременно.
* **Сервер, nginx, gunicorn, сертификат** — нет. Замер в момент отказа
  (`down.sh`, 3 августа) дал 200 на всех четырёх слоях, включая заход
  через публичный адрес; журнал nginx молчал два часа подряд.

Главное, что дал этот замер: **в журнале gunicorn видно, как телефон и
компьютер владельца получают код 200 и полные 39 221 байт ровно в те
минуты, когда страница у них не открывалась.** Значит запрос до сервера
доходит и ответ формируется — ломается обратный путь, доставка ответа
посетителю. Дальше искать надо там: `client.sh` и проверка размером.

### Если с телефона таймаут, а с компьютера открывается

Проверка, которая сузила поиск сильнее всего: со страницы убрали CSS
и скрипты, оставив один-единственный запрос, — и с телефона всё равно
«превышено время ожидания». Одновременно с компьютера сайт открывался
нормально, сервер отвечал 200 на все внутренние проверки.

Из этого следует: **дело не в сайте.** Соединение с телефона не доходит
до конца ещё до того, как начинается разговор по HTTP. Таймаут — это
не ошибка сервера, это «не достучался».

#### Что показали проверки с телефона

1. **`http://159.194.230.39/` открывается.** Обычное соединение до
   сервера проходит, nginx отвечает. Маршрут цел, адрес не заблокирован,
   порт 80 работает. Ломается что-то в HTTPS.
2. **AAAA-записи у домена нет** — в DNS только `A 159.194.230.39`.
   Значит по IPv6 телефон к сайту и не пойдёт, даже имея IPv6.
   **Версия про IPv6 отпадает полностью.**
3. **Телефон ходит через VPN.** `test-ipv6.com` показал провайдера
   `LAGOM PRODUCTS LLC, AM` и адреса `2.26.13.3` / `2a09:3f00:3302:4::1`
   — при том, что телефон физически в Красноярске. Одинаково и по Wi-Fi,
   и по мобильной сети, то есть туннель включён на самом устройстве.

Пункт 3 — и есть настоящая разница между телефоном и компьютером.
Дело не в «мобильной сети»: компьютер ходит напрямую, телефон — через
туннель.

#### Причина: обрыв определения размера пакета (PMTU) в туннеле

> **Версия не подтвердилась.** VPN оказался включён и на компьютере,
> где сайт открывается, а на телефоне без VPN сайт всё равно не открылся.
> Раздел оставлен как справка по PMTU — само явление реально и однажды
> может пригодиться, но к этой поломке отношения не имеет.

VPN добавляет к каждому пакету свой заголовок, поэтому внутри туннеля
помещается меньше данных, чем в обычной сети (обычно около 1380 байт
вместо 1500). Сервер об этом не знает и шлёт полноразмерные пакеты.
Промежуточный узел должен ответить служебным сообщением ICMP «пакет
великоват», но его почти всегда режут файрволы. Пакеты молча пропадают,
соединение висит до таймаута.

Это ровно объясняет всё, что наблюдалось:

* `http://…` по адресу открывается — ответ 404 занимает пару сотен байт
  и в маленький пакет помещается;
* `https://s-poryadok.ru/` виснет — при установке HTTPS сервер шлёт
  цепочку сертификатов на несколько килобайт, это как раз крупные пакеты;
* ssh «вылетал через несколько секунд» — обмен ключами тоже крупный;
* с компьютера всё работает — там туннеля нет, размер пакета обычный.

**Решающая проверка:** выключить VPN на телефоне и открыть
`https://s-poryadok.ru/`. Открылось — причина подтверждена.

Лечение на сервере (нужно в любом случае: у посетителей тоже бывают
VPN и корпоративные туннели):

```bash
sysctl net.ipv4.tcp_mtu_probing          # скорее всего 0
sudo sysctl -w net.ipv4.tcp_mtu_probing=1
echo 'net.ipv4.tcp_mtu_probing=1' | sudo tee -a /etc/sysctl.conf
```

При значении 1 ядро само уменьшает пакеты, когда замечает, что они
пропадают. Настройка безопасная и обратимая.

Дополнительно — сразу договариваться о меньшем размере пакета при
установке соединения, не дожидаясь потерь:

```bash
sudo iptables -t mangle -A POSTROUTING -p tcp --tcp-flags SYN,RST SYN \
  -j TCPMSS --clamp-mss-to-pmtu
```

Чтобы правило пережило перезагрузку:

```bash
sudo apt install -y iptables-persistent
sudo netfilter-persistent save
```

И убедиться, что нужный ICMP не режется на самом сервере:

```bash
sudo iptables -L INPUT -n | grep -i icmp
```

Строк с `DROP` для `icmp` быть не должно.

#### Если и это не помогло

Остаётся блокировка на стороне самого VPN-сервиса или его провайдера —
тогда сайт недоступен только через конкретный туннель, а у всех
остальных посетителей открывается. Проверяется тем же выключением VPN
и заходом с чужого телефона.

### Логи после перезагрузки

`dmesg` очищается при ребуте и после него ничего не покажет. Журнал
предыдущей загрузки смотрится так:

```bash
journalctl --list-boots                  # список загрузок
sudo journalctl -k -b -1 | grep -i -E 'oom|killed process|blocked'
sudo journalctl -u gunicorn -b -1 | tail -50
sudo journalctl -u nginx -b -1 | tail -30
```

Если журнал не сохраняется между загрузками, включить:

```bash
sudo mkdir -p /var/log/journal && sudo systemd-tmpfiles --create --prefix /var/log/journal
sudo systemctl restart systemd-journald
```

### Наблюдение за состоянием

В репозитории есть `scripts/watch.sh` — раз в 30 секунд пишет в
`logs/watch.log` память, swap, load average, место на диске, число
процессов gunicorn, количество соединений и то, отвечает ли сайт
через сокет и через nginx. Файл остаётся на диске после перезагрузки,
поэтому по нему видно, что происходило в минуты перед падением.

```bash
cd /var/www/s-poryadok
nohup ./scripts/watch.sh >/dev/null 2>&1 &
```

Посмотреть последние записи:

```bash
tail -50 /var/www/s-poryadok/logs/watch.log
```

Остановить: `pkill -f scripts/watch.sh`

### Что ещё проверить

```bash
df -h                    # закончившееся место ломает всё разом
sudo nginx -t            # ошибка в конфиге
ss -s                    # сколько открытых соединений
uptime                   # перезагружался ли сервер сам
```

**IPv6.** У домена сейчас только `A`-запись, AAAA нет, поэтому по IPv6

```bash
nslookup -type=AAAA s-poryadok.ru
curl -6 -sS -o /dev/null -w '%{http_code}\n' https://s-poryadok.ru/   # с сервера
```

## Память

На проверенном сервере (2 ГБ, два воркера) памяти хватает с запасом, и
падений из-за неё пока не зафиксировано. Раздел оставлен на будущее:
запас невелик, и при росте трафика память станет узким местом первой.

**Что было.** `pandas` импортировался на уровне модуля в `landing/views.py`,
а URL-конфиг тянет views целиком. Из-за этого pandas вместе с numpy жил
в памяти каждого воркера — даже когда человек просто открывал главную.
Замер: **99 МБ на воркер против 55 МБ без него.** При четырёх воркерах это
лишние 176 МБ на пустом месте.

**Что сделано.** Импорт перенесён внутрь `express_audit` — единственного
места, где pandas нужен. Обычные страницы за него больше не платят.

### Проверить, было ли переполнение памяти

```bash
free -h                                  # сколько свободно сейчас
sudo dmesg -T | grep -i -E 'oom|killed process' | tail -20
sudo journalctl -u gunicorn --since '2 days ago' | grep -i -E 'worker|oom|sigkill' | tail -30
ps -o pid,rss,cmd -C gunicorn --sort=-rss   # сколько ест каждый воркер
```

Если в `dmesg` есть строки вида `Out of memory: Killed process ... gunicorn` —
диагноз подтверждён.

### Сколько держать воркеров

Формула «2 × ядра + 1» рассчитана на серверы с запасом памяти. Для сайта
с небольшим трафиком на маленьком VPS двух-трёх воркеров достаточно,
и лучше иметь запас памяти, чем незанятые воркеры.

Открыть настройку службы:

```bash
sudo systemctl edit --full gunicorn
```

В строке `ExecStart` задать явно:

```
--workers 3 --max-requests 500 --max-requests-jitter 50 --timeout 60
```

`--max-requests` заставляет воркер перезапускаться каждые N запросов —
дешёвая страховка от утечек памяти: даже если что-то течёт, оно не
накапливается сутками. `jitter` разводит перезапуски по времени, чтобы
воркеры не ушли перезагружаться разом.

Применить:

```bash
sudo systemctl daemon-reload
sudo systemctl restart gunicorn
```

### Файл подкачки

Если его нет, любой всплеск памяти сразу убивает процессы. Гигабайт swap
не заменяет память, но превращает падение сервера в кратковременное
замедление:

```bash
free -h | grep -i swap          # если строка пустая или нули — swap нет
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

## Если что-то сломалось

| Симптом | Куда смотреть |
|---|---|
| 502 Bad Gateway | `sudo systemctl status gunicorn`, `sudo journalctl -u gunicorn -n 50` |
| Сайт без стилей | не выполнен `collectstatic`, либо путь в `location /static/` не совпадает с `STATIC_ROOT` |
| 500 на всех страницах | `logs/app.log`, `sudo journalctl -u gunicorn -n 50` |
| Заявка не приходит в Telegram | колонка «в TG» в списке заявок; сама заявка при этом сохранена. Проверить `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` в `.env` |
| Изменения не видны | не перезапущен `gunicorn` |
| Бесконечный редирект | включён `SECURE_SSL_REDIRECT=True` при том, что редирект уже делает Nginx |
| Сервер перестал отвечать целиком, помогает только перезагрузка | нехватка памяти — см. раздел «Память» выше |

Откатиться на предыдущую версию:

```bash
cd /var/www/s-poryadok
git log --oneline -5
git checkout <хеш-рабочего-коммита>
sudo systemctl restart gunicorn
```
